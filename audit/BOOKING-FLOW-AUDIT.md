# Meeting form handoff — 6.12.8

## Findings and corrections

Dynamic questions were retained under opaque keys but omitted from cart, WooCommerce emails and account/admin order details. Modern loc_* selections lacked historical readable labels. Already-unslashed cart values were passed through wp_unslash again when promoted to order meta, stripping legitimate backslashes. Custom email name fallback indexed WooCommerce items by zero rather than their item IDs. Scheduling failures lost detailed errors and response bodies. An order awaiting its webhook could submit another POST /invitees. Tracking used the displayed order number, which is not necessarily the numeric WooCommerce order ID used for webhook lookup.

Server-owned question and location labels now travel with the cart, line item and order snapshot. A shared renderer provides readable labels, exact selected time in the site timezone, location details, all submitted answers, multiselect/Other answers and legacy notes in HTML or plain text. Unicode and multiline text survive; HTML values are escaped and line breaks retained. Renderers are used in cart, WooCommerce emails, account/admin order details, thank-you pages and Calendly custom emails. Custom email templates can place {meeting_details}; templates without it receive the details appended. Historical response/request metadata and cached question definitions provide legacy label fallback. Historical fields that were never persisted cannot be reconstructed.

Location details are required only for selected invitee-input kinds, with frontend and server validation before checkout. Multiselect and single-select forms offer Other text. The scheduling worker sends selected location.kind and location.location when relevant, excluding host metadata; omits location for round robin and includes the sole configured location for older forms. It shares frontend question keys and sends exact Calendly question names, including original whitespace. Enabled Order ID questions are supplied automatically with the numeric order ID. Tracking also uses that ID. Exact selected UTC slot and sanitized billing identity remain the booking source; unsupported fixed-offset API timezone strings fall back to IANA UTC.

Each scheduling attempt persists _cb_calendly_create_request, _cb_calendly_create_http_status, _cb_calendly_create_response_body and _cb_calendly_create_received_at. Successful invitee resources remain in _cb_calendly_create_response and management URLs are stored separately. Failed responses retain parameter-specific diagnostics. A response missing invitee/event identity is not accepted as success. Orders with an accepted invitee awaiting webhook are not re-posted. The existing confirmation flow still waits for webhook reconciliation.

## Validation

31 booking-flow checks passed against real WooCommerce capture, line-item/order persistence, rendering, worker POST serialization and response capture using mocked Calendly HTTP. The temporary order was deleted; its queued retry was canceled. Mail was intercepted and external HTTP blocked throughout the fixture. Tests cover Unicode, newlines, apostrophes, backslashes, escaped HTML, multiselect/Other, precise question text, location inputs, UTC slots, numeric tracking ID, HTTP 201 and 400 capture, and no repeated POST while awaiting webhook.

The 64 existing API/availability/dashboard/export checks also passed: 95 total. PHP lint passed on 54 source files; JavaScript syntax passed on nine. The read-only comparison found no existing WooCommerce orders with stored scheduling responses, so no live invitees could be compared. No live appointment was created, no real email sent, and no live webhook confirmation or browser checkout was exercised. A live booking on this account remains necessary to verify token write scope, account eligibility and real notification/webhook delivery. Concurrent-worker locking and ambiguous transport-timeout reconciliation were not redesigned in this patch.
